# دلگرمی

سایت و پنل تیم دلگرمی (delgarmi.com). معماری، مدل داده و مراحل ساخت در سند «دلگرمی — پیشنهاد فنی (قدم ۴)» آمده است.

| پوشه | چیست |
| --- | --- |
| `web/` | سایت: Next.js 16.3، React 19.3، TypeScript |
| `api/` | API و پنل تیم: Django 5.2، Django REST Framework 3.18، Python 3.13 |
| `deploy/` | تنظیمات nginx و اسکریپت انتشار |
| `docker-compose.yml` | پنج سرویس روی یک سرور: nginx، web، api، worker، db |

## اجرای محلی

سایت:

```bash
cd web
npm ci
npm run dev          # http://localhost:3000 ، کامپوننت‌ها: /design-system
```

بک‌اند (به PostgreSQL نیاز دارد):

```bash
docker run -d --name delgarmi-db -e POSTGRES_DB=delgarmi -e POSTGRES_USER=delgarmi -e POSTGRES_PASSWORD=local -p 127.0.0.1:5432:5432 postgres:18-alpine
cd api
python3.13 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
export DJANGO_DEBUG=1 PANEL_PATH=panel-local POSTGRES_HOST=127.0.0.1 POSTGRES_PASSWORD=local
python manage.py migrate && python manage.py runserver   # پنل: http://localhost:8000/panel-local/
```

## تست‌ها

```bash
cd api && python -m pytest        # با همان متغیرهای PostgreSQL بالا
cd web && npm test && npm run build
```

تست‌های مرورگر صفحه‌ها را با API واقعی می‌سنجند. برای اجرای محلی، API را روی پورت ۸۰۰۰ بالا بیاورید و بعد:

```bash
cd web && npx playwright install chromium
npm run build && npm run start &   # درخواست‌های /api/ به 127.0.0.1:8000 می‌رود
npm run test:e2e
```

GitHub Actions روی هر push و Pull Request: تست‌های Django با PostgreSQL 18، تست‌های واحد و ساخت سایت، و بعد کل پنج سرویس را با Docker و یک گواهی آزمایشی بالا می‌آورد و تست‌های مرورگر را از پشت nginx اجرا می‌کند (axe، کیبورد، عرض‌های ۳۲۰ تا ۱۹۲۰، همه‌ی لینک‌ها، شهرها و خدمت‌ها، روی دسکتاپ و گوشی). فقط وقتی همه سبز باشد سرور نسخه‌ی تازه را می‌گیرد.

## متن‌ها و جاهای خالی

- متن صفحه‌ها در `web/content/` است: `services.ts` (چهار خدمت)، `faq.ts`، `nav.ts`.
- `web/content/facts.ts` چیزهایی را نگه می‌دارد که فقط تیم دلگرمی می‌داند: تلفن، ساعت کاری، زمان تماس بعد از درخواست، نام حقوقی و نشانی. تا وقتی مقداری `null` است، سایت متن نمونه‌اش را با زمینه‌ی کهربایی و زیرخط نقطه‌چین نشان می‌دهد (دکمه‌ی تماس هم تا آمدن شماره خاکستری است)؛ با پر کردنش همه‌ی صفحه‌ها درست می‌شوند.
- در همان فایل، `PENDING_POLICIES` متن‌هایی را نام می‌برد که هنوز پیش‌نویس‌اند یا تأیید لازم دارند (هزینه، جایگزینی مراقب، لغو، مرجع مجوز و...). سایت کنارشان برچسب کوچک «پیش‌نویس» یا «نیاز به تأیید» می‌گذارد. وقتی یکی قطعی شد، کلیدش را پاک کنید؛ TypeScript همه‌ی جاهایی را که به آن اشاره می‌کنند نشان می‌دهد.

## شهرها و خدمت‌ها در پنل

- ۱٬۳۵۴ شهر از داده‌ی مرکز آمار (`api/catalog/data/`) و چهار خدمت در دیتابیس‌اند. هیچ خدمتی در هیچ شهری از پیش روشن نیست.
- در پنل، «شهرها» را باز کنید، شهر را پیدا کنید (ي/ی، ك/ک و فاصله فرقی نمی‌کند) و خدمت‌های حضوری فعالش را تیک بزنید. سایت تا یک دقیقه بعد همین را نشان می‌دهد.
- روان‌درمانی آنلاین همیشه در همه‌ی شهرها فعال است؛ تیک روان‌درمانی یعنی جلسه‌ی حضوری هم دارد.
- ۶۷ شهر بزرگ صفحه‌ی خودشان را دارند (`/cities/isfahan`). برای شهر دیگری صفحه بخواهید، در پنل «نشانی صفحه» را پر کنید. صفحه‌ی شهری که هنوز هیچ خدمت حضوری ندارد برای موتورهای جست‌وجو noindex است و در sitemap نمی‌آید.

## فرم درخواست

- سؤال‌ها، گزینه‌ها، شرط‌ها و متن‌های فرم همه در `api/catalog/form.json` است. API هر درخواست را با همین فایل می‌سنجد و سایت آن را از `/api/form` می‌گیرد؛ پس فقط یک نسخه وجود دارد. برای عوض کردن یک سؤال همین فایل را عوض کنید؛ تست‌های هر دو طرف آن را می‌خوانند.
- مقدار گزینه‌ها (مثل `night` یا `injection`) همان چیزی است که لینک‌های صفحه‌ی خدمت در نشانی می‌فرستند (`?type=night`). اگر لینکی به گزینه‌ای اشاره کند که در فرم نیست، `npm test` شکست می‌خورد.
- پاسخ‌های نیمه‌کاره فقط در مرورگر خود کاربر می‌ماند (حداکثر ۷ روز) و بعد از ثبت پاک می‌شود. تأیید شماره یک توکن نیم‌ساعته است که فقط در همان تب مرورگر می‌ماند و با آن فقط یک درخواست ثبت می‌شود.
- API هر درخواست را دوباره با همان قاعده‌ها می‌سنجد: پاسخی که به آن خدمت ربط ندارد ذخیره نمی‌شود (مثلاً شهرِ جلسه‌ی آنلاین یا روز شروعِ پرستاری فوری). اگر خدمتِ آن شهر در پنل روشن باشد وضعیت «جدید» است، وگرنه «لیست انتظار». روان‌درمانی آنلاین همیشه «جدید» است.
- درخواست‌ها در پنل، بخش «درخواست‌ها» دیده می‌شوند (فعلاً فقط دیدنی؛ تغییر وضعیت و تماس در مرحله‌ی ۴ می‌آید). خانواده‌ها در «خانواده‌ها» و پیامک‌ها در «صف پیامک».

### پیامک و کد تأیید

تا وقتی حساب سرویس پیامک وصل نشده (`SMS_BACKEND=log`، پیش‌فرض)، هیچ پیامکی فرستاده نمی‌شود و متن هر پیامک در لاگ نوشته می‌شود. یعنی تا آن موقع خانواده‌ها نمی‌توانند فرم را تا آخر پر کنند؛ فقط کسی که به سرور دسترسی دارد کد را می‌بیند. کد تأیید را روی سرور با این دستور ببینید:

```bash
cd /opt/delgarmi && docker compose logs --since 15m api | grep OTP
```

پیامک «ثبت شد» و «لیست انتظار» را worker از صف می‌فرستد و در `docker compose logs worker` دیده می‌شود. اگر فرستادن نشد، دوباره امتحان می‌کند (۲، ۴، ۸ … دقیقه بعد، حداکثر یک ساعت) و بعد از ۸ بار «فرستاده نشد» می‌شود.

قاعده‌های کد (در `api/config/settings.py`): هر کد ۵ رقم و ۲ دقیقه معتبر است؛ کد بعدی برای همان شماره بعد از ۲ دقیقه؛ حداکثر ۵ کد در ساعت برای هر شماره و ۲۰ کد در ساعت از هر IP؛ ۵ بار کد اشتباه کد را باطل می‌کند؛ تأیید شماره نیم ساعت اعتبار دارد. خود کد هیچ‌جا ذخیره نمی‌شود، فقط هش آن با کلید مخفی سرور. متن خطاهای فرم (`form.json`) همین عددها را نام می‌برد؛ با هم عوضشان کنید.

## سرور و انتشار

نصب سرور یک دستور است. روی یک سرور خالی Ubuntu یا Debian، با root:

```bash
bash install-delgarmi.sh
```

`install-delgarmi.sh` همان `deploy/install.sh` است. خروجی‌اش انگلیسی است و این کارها را خودش انجام می‌دهد:

- نصب Docker و افزودن swap روی سرورهای کم‌رم
- باز کردن ۸۰ و ۴۴۳ در ufw و صبر تا DNS دامنه برسد
- گرفتن گواهی Let's Encrypt و تنظیم تمدید خودکار آن
- ساختن رمزهای تصادفی در `/opt/delgarmi/.env`
- ساختن ایمیج‌ها، بالا آوردن پنج سرویس و روشن کردن به‌روزرسانی خودکار

تنها کار دستی یک بار است: اسکریپت یک کلید فقط‌خواندنی چاپ می‌کند که باید در Settings ← Deploy keys مخزن اضافه شود. اسکریپت منتظر می‌ماند و بعد خودش ادامه می‌دهد. اجرای دوباره‌اش بی‌خطر است و رمزها، گواهی و داده‌ها را نگه می‌دارد.

انتشار خودکار است: هر push روی `main` که همه‌ی تست‌هایش سبز شود، شاخه‌ی `release` را به همان commit می‌برد. سرور هر دقیقه `release` را نگاه می‌کند و اگر جلو رفته باشد، ایمیج‌ها را می‌سازد و سرویس‌ها را دوباره بالا می‌آورد (`deploy/update.sh`). اگر نسخه‌ی تازه سالم بالا نیاید، به نسخه‌ی قبل برمی‌گردد و آن commit را رد می‌کند تا commit بعدی برسد.

روی سرور:

```bash
delgarmi status    # نسخه‌ی در حال اجرا، آخرین بررسی، سلامت سایت، تاریخ انقضای گواهی
delgarmi update    # همین حالا به‌روز کن
delgarmi logs      # گزارش انتشارها و سرویس‌ها
```

## سیستم طراحی

`web/design/tokens.json` و `web/design/components.css` کپی بدون تغییر سیستم طراحی‌اند. تغییر اول در سیستم طراحی انجام می‌شود و بعد این دو فایل دوباره کپی می‌شوند. `styles/tokens.css` در هر build از روی `tokens.json` ساخته می‌شود و یک تست مطمئن می‌شود هر متغیری که CSS به کار می‌برد تعریف شده باشد.
